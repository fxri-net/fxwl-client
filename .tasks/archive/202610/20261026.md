# GitLab CI 改用国内镜像并缓存 Electron 二进制

批次：1　计划位置：1/1　前置：无

## 背景

上一轮在 `.test-setup` 设 `ELECTRON_SKIP_BINARY_DOWNLOAD: "1"`，安装阶段不再访问 github.com，`pnpm install` 通过；但 `pnpm verify` 的 build 阶段随即失败：`[vite:bytecode] Electron uninstall`。

定位代码后确认此前的判断有误——`electron-vite` 的 `compileToBytecode` 并不是纯运行期行为：它调用 `getElectronPath()` 读取 `node_modules/electron/path.txt`，再以 `ELECTRON_RUN_AS_NODE=1` 拉起 Electron 二进制执行 `bin/electron-bytecode.cjs` 生成 `.jsc`。二进制缺失即抛 `Electron uninstall`，因此跳过下载与 bytecode 编译不可共存。

Runner 能访问 registry.npmjs.org，仅 github.com 直连超时，故改走国内镜像下载；再用 GitLab cache 缓存下载产物，避免 `verify` 与 `pages` 每次都重下约 92MB。

## 实施方案

- `.gitlab-ci.yml` 的 `.test-setup`：
  - 删去 `ELECTRON_SKIP_BINARY_DOWNLOAD`，改为 `ELECTRON_MIRROR: "https://npmmirror.com/mirrors/electron/"` 与 `ELECTRON_CUSTOM_DIR: "{{ version }}"`（npmmirror 的目录不带 `v` 前缀，而 `@electron/get` 默认取 `details.version`）。
  - `electron_config_cache: "$CI_PROJECT_DIR/.cache/electron"`，把下载缓存落在项目目录内。
  - `cache` 以 `electron-$CI_COMMIT_REF_SLUG` 为 key、路径 `.cache/electron/`，两个 job 共享同一分支的缓存；缓存内部按下载 URL 的目录哈希分桶，Electron 升级也不会串包。
- `.gitignore` 增加 `/.cache`，避免本地跑 CI 等价命令时缓存目录出现在工作区。

## 影响范围

- 仅 GitLab CI 安装阶段与缓存配置；`verify` / `pages` 的执行内容不变，bytecode 仍照常编译与校验。
- 本地开发、GitHub Actions、`electron-builder.yml` 的 `electronDist` 均不受影响（这些环境不设镜像变量，仍走默认源）。

## 验证方式

- `pnpm verify`：与 CI 同源的聚合验收。
- 推送后观察 GitLab pipeline：安装阶段应从 npmmirror 下载并通过，build 阶段不再报 `Electron uninstall`；随后 pipeline 命中 cache 时安装阶段不再下载。

## 实施结果

- `.gitlab-ci.yml` 的 `.test-setup` 删除 `ELECTRON_SKIP_BINARY_DOWNLOAD`，改为 `ELECTRON_MIRROR: "https://npmmirror.com/mirrors/electron/"`、`ELECTRON_CUSTOM_DIR: "{{ version }}"`、`electron_config_cache: "$CI_PROJECT_DIR/.cache/electron"`，并加 `cache`（`key: electron-$CI_COMMIT_REF_SLUG`，路径 `.cache/electron/`）；`verify` 与 `pages` 分处 test / deploy 两个 stage，串行执行时后者直接命中前者上传的缓存。
- `.gitignore` 增加 `/.cache`。
- 镜像地址有效性已实测：按同样的环境变量调用 `@electron/get` 的 `getArtifactRemoteURL`，解析出 `https://npmmirror.com/mirrors/electron/22.3.27/electron-v22.3.27-linux-x64.zip`，HEAD 请求返回 200（重定向至 cdn.npmmirror.com）；YAML 用 js-yaml 解析，anchor 合并后的 `variables` / `cache` 均落在 `verify` 与 `pages` 上。
- 验证命令：`pnpm verify`（lint → typecheck ×3 → vitest 16 项 → electron-vite build，bytecode 正常产出 `index.jsc`）。

> 负责人：唐启云　状态：已完成　范围：app　完成时间：2026-10-26 02:04

# 导航胶囊外观与隐藏时机调整

延续 导航胶囊热区唤起与文案归一（见 archive/202610/20261026.md）。

## 一、背景

热区唤起方案落地后仍有三处不符合展厅展示诉求：

- 胶囊底色为不透明纯白，浮在网页与视频之上时像一块贴在画面里的白板，割裂感明显。
- 胶囊与按钮均用 `border-radius: 999px` 的胶囊形，圆角造型与展示内容无关，属于多余的装饰语言。
- 鼠标移出后仍要等 `IDLE_DELAY`（3000ms）才隐藏，离开后导航还会滞留一段时间；进入页面时又有一次 3 秒的位置引导，展示开始阶段页面上仍多出内容以外的元素。

## 二、实施方案

- `.capsule` 背景改深色半透明 `rgba(0, 0, 0, 0.55)`，边框改半透明白，文字与 hover 态一并转白，保证压在浅色与深色内容上都可读。
- 去掉 `.capsule` 与 `.item` 的 `border-radius`，改为直角。
- `leaveActive` 去掉 3 秒计时，`pointerleave` / `focusout` 立即置 `active = false`，保留 160ms 淡出过渡。
- 去掉挂载时的 3 秒引导；`IDLE_DELAY` 收窄为仅服务快捷键亮相的 `FLASH_DELAY`，避免胶囊被快捷键唤起后无限滞留。

## 三、影响范围

`src/renderer/src/components/NavCapsule.vue` 与外层热区、`docs/manual.md` 的导航胶囊说明。不涉主进程、预加载与配置项。

## 四、验证方式

- `pnpm verify` 通过
- `pnpm dev` 下进入 `/client/index`：进页面不显示胶囊；移入热区显现为深色半透明直角条；移出立即消失；快捷键触发后亮 3 秒自行隐藏

## 五、回滚方案

还原 `NavCapsule.vue` 与 `docs/manual.md`；已提交则按提交哈希回退。

## 六、实施结果

- `NavCapsule.vue` 胶囊底改 `rgba(0, 0, 0, 0.55)`、边框改半透明白、阴影加深，按钮文字与 hover 底色一并转白；`.capsule` 与 `.item` 的 `border-radius` 全部移除。
- `leaveActive` 只清计时器并立即置 `active = false`，`pointerleave` / `focusout` 即刻隐藏，仅保留 160ms 淡出过渡；`IDLE_DELAY` 更名 `FLASH_DELAY`，只在 `flash` 递增时启动 3 秒计时；挂载时的引导逻辑与 `onMounted` 引用删除。

> 负责人：唐启云　状态：已完成　范围：app　完成时间：2026-10-26 01:45

# 内嵌页销毁报错修复

计划位置：阶段六 内嵌页收口 第 1 项；前置：无。

## 一、背景

展厅大屏在 `/client/index` 点击「退出」后，主进程弹出 `Uncaught Exception: TypeError: Object has been destroyed`，栈落在 `out/main/index.js` 的 `onceWrapper` 与 `EventEmitter.emit`。根因是 `src/main/security.ts` 销毁监听回调内再次访问已销毁的内嵌页对象取 `session`：`guest.once("destroyed", () => guest.session.clearStorageData())`。离开内嵌页或退出应用都会走到该回调，不止点击按钮这一条路径。

## 二、实施方案

- `prepareGuest` 挂载销毁监听前先取出 `guest.session` 引用，回调只依赖该引用，不再触碰已销毁的 `guest`。
- 会话清理补 `catch` 并输出告警，避免退出流程中会话已不可用时产生未捕获的 Promise 拒绝。

## 三、影响范围

仅主进程内嵌页会话清理时机与异常处理；不涉导航策略、安全策略与渲染层代码。

## 四、验证方式

- `pnpm verify` 通过
- `pnpm dev` 下进入 `/client/index` 点「返回首页」不再弹主进程异常框
- 关闭应用窗口退出，终端与界面均无 `Object has been destroyed`

## 五、回滚方案

还原 `src/main/security.ts` 单文件改动；已提交则按提交哈希回退。

## 六、实施结果

- 改动：`prepareGuest` 内把 `guest.session` 提到监听挂载之前缓存为 `guestSession`，`once("destroyed")` 回调只使用该引用调用 `clearStorageData()`，并补 `.catch` 输出 `[guest] 会话清理失败：` 告警。
- 根因对应：报错栈 `onceWrapper → EventEmitter.emit` 正是 `once` 包装后的销毁事件回调；原写法在回调内读 `guest.session`，此时 `WebContents` 已销毁，属性访问即抛 `Object has been destroyed`。
- 覆盖路径：显式离开内嵌页（返回首页）、应用退出、路由重建导致的内嵌页卸载都走同一回调，一并修复。
- 验证：`pnpm verify`（lint → typecheck ×3 → vitest 16 例 → build）全绿；`pnpm dev` 主进程与预加载构建成功、应用启动后终端无异常输出。
- 边界：点击「返回首页」的交互链路未在本轮自动化中复现，依据是报错栈与该回调一一对应、修复后回调不再触碰已销毁对象；如后续改内嵌页会话策略需重新人工过一遍。
