# 全端通用规范（common）

> 归属：common（所有端适用）。条文全文见本节，索引见 index.md。

## C-1. 任务区不出现外部仓库实名

`.tasks/` 内文本指称本仓以外的仓库时，一律用通用措辞，不得写实名。

- **要求**：任务档正文、归档叙述与 frontmatter 字段值凡需提及本仓以外的仓库，须改用「接入方仓库」「被参考仓库」「外部仓库」这类通用称谓；做技术验证或对照参考时同样只写泛称，不得列举被参考对象的实名清单。判据取**是否以具体名称指涉某个外部仓库**，与 `C-2` 的路径判据正交；依赖包名、被调接口名等本仓事实照写。
- **反例**：在背景或归档叙述里列出下游仓库实名（如「被甲仓、乙仓等 8 个项目以源码拷贝方式复用」），或把实名当作 frontmatter 字段的示例值。本仓文本随 git 分发后即携带外部仓库的目录命名，而读者只具本仓视角、无从判断该名与本仓的关系。
- **理由**：任务区是仓库自述面，只承载本仓事实；实名指涉外仓既污染本仓文本，又把某次会话偶发的参照对象固化成仓库事实，还随分发外泄无关仓库信息。
- **配套**：与全局技能 `skills/fxri-plan-to-task/references/task-spec.md` 的「跨仓库改动各自归档」配套——该纪律管「记不记他仓的事」（视角），本条管「写不写他仓的名」（用词），两者同属任务区文本治理。该纪律已在全局层承载，本载体不另立条文。

## C-2. 路径书写与归档归一

仓库内引用用仓库根相对路径；本机绝对路径只允许存在于进行中的任务档，归档时须归一为占位形式。

- **要求**：仓库内引用一律用以仓库根为基准的相对路径（含行号时形如 `src/main/index.ts L12`），不得写指向本机的绝对 `file:///` 链接。分两阶段：任务进行中可保留需要以绝对路径索引的本机资源路径（设计素材、仓库外规则文件、本机解释器），便于当场定位；**归档时须归一**为占位形式——仓库外文件 `<本机>/…`、家目录 `~/` 或 `%USERPROFILE%`，仅保留可辨识的末段文件名。
- **反例**：在任务档写入本机解释器的完整安装路径后直接归档。该路径对他人不可用，且暴露作者本机的软件安装布局。
- **理由**：本机绝对路径随 git 分发后对他人无意义，且泄露作者本机目录结构。两阶段口径保留「进行中当场可定位」的便利，同时把泄露面收敛在未归档的临时文本里。
- **配套**：归一属归档写入时的形态处理，不构成对已归档块的追改；归档后发现遗漏的，按全局技能的「事实更正」通道追加修订记录。

## C-3. 业务前缀统一为 fx

业务侧的设计令牌、样式类名、运行时选择器与会话分区名一律以 `fx` 为前缀，不引入其他变体。

- **要求**：CSS 自定义属性写 `--fx-*`，SCSS 变量写 `$fx-*`，样式类名写 `.fx-*`（如 `.fx-layout`、`.fx-panel`），会话分区名写 `fx-<用途>`（如 `fx-client`）。按名字在运行时查找的选择器字符串（如 Element Plus 的 `appendTo`）须与类名同源同步。历史归档文本不追改。
- **反例**：同仓并存 `--fxy-*` 与 `--fx-*`；把类名改成 `.fx-layout` 却漏改 `appendTo = ".fxy-layout"`，弹层因找不到容器退回挂到 `body`，定位错乱。
- **理由**：前缀是全仓检索的锚点，变体并存会让 grep 失去完整性保证；令牌漏改不会报错而是静默失效（颜色、间距回落默认值），只能靠「残留检索归零」兜住；选择器字符串与类名拆开改则会引入难定位的运行时布局问题。

## C-4. 用例集中在 src/__tests__

测试文件一律放在 `src/__tests__/`，不与业务代码同目录，命名与被测模块同名。

- **要求**：用例目录固定为 `src/__tests__/`，文件名取被测模块名（如 `contract.test.ts`、`config.test.ts`），跨端用例同目录、以模块名区分；`vitest.config.ts` 的 `include` 只覆盖该目录；两套业务 tsconfig 通过 `exclude: ["src/__tests__/**/*"]` 把用例排除在类型检查之外；需要 DOM 的用例在文件头声明 `// @vitest-environment jsdom`。
- **反例**：把用例与业务文件同目录混放（如 `src/shared/config.test.ts`），或用例落在 tsconfig 的 `include` 范围内，导致测试代码进入构建面与类型检查面。
- **理由**：目录职责单一，增补用例不改动业务目录结构；集中后 `include` 与 `exclude` 只有一处维护点，也不会出现「业务目录里混入用例、类型检查按业务口径报错」这类耦合。
